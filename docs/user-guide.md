# Slurm 集群监控 — 用户使用手册

本手册面向**普通用户**（查看自己/他人作业的使用情况），
按「先配置显示名 → 再看页面 → 最后看个人统计」的顺序说明。
管理员的集群配置（项目组、节点映射）见单独的
[管理员配置手册](admin-guide.md)。

访问地址：

- Web 界面：`http://192.168.3.102:8000/`
- API 文档：`http://192.168.3.102:8000/docs`

页面顶部导航共 6 个标签：

| 标签 | 用途 |
|------|------|
| 总览 | 集群整体资源、用户排行榜、节点列表 |
| GPU 详情 | 单节点历史曲线、显卡实时状态、节点上的作业 |
| 排队作业 | 全集群排队情况、等待原因 |
| 个人统计 | 单个用户的 GPU 耗时、作业列表、单作业效率分析 |
| 名字映射 | 把 Slurm 账号映射成姓名，并归属项目组 |
| 集群配置 | 管理员登录后维护项目组与算力节点 IP |

## 一、先做一次名字映射（推荐）

系统本身拿到的是 Slurm 账号（如 `zhangsan`）。映射后，下拉框、排行榜、作业列表里都会显示**姓名**，
找人、看统计都方便。**映射只影响展示，不改动 Slurm 账号本身，也不影响作业提交和调度。**

### 操作步骤

1. 点击顶部导航 **「名字映射」**。
2. 页面分两块：
   - **待映射用户**：还没有显示名的账号（显示名为 `—`）
   - **已映射用户**：已经有显示名的账号
3. 在「待映射用户」里找到自己的账号，点击行右侧 **「设置」**。
4. 行内会出现编辑框：
   - **显示名称**：填真实姓名（如 `张三`）。**必须全局唯一**，不能和其他人重名。
   - **项目组**：按住 `Ctrl` / `Cmd` 可多选。项目组由管理员在「集群配置 → 项目组」里预先建好；
     列表为空说明还没建，可先跳过。
5. 点 **「保存」**。成功后该账号会从「待映射用户」移到「已映射用户」。

之后修改：在「已映射用户」里点 **「编辑」**，改完保存即可。

### 说明与注意事项

- **搜索结果**：顶部搜索框可按账号或显示名过滤两张表。
- **重名/冲突**：如果提示「显示名已被其他账号使用」，换一个名字；如果要给多个账号合并成同一个显示名，
  请联系管理员处理（页面也有同样提示）。
- **并发修改**：映射带版本号保护。如果两个人同时改同一条记录，后保存的人会看到
  「数据已被其他人修改，请刷新后重试」，刷新页面再改即可。
- 保存后，**排队作业页**和**个人统计页**的用户下拉框会自动刷新为姓名，不需要重新登录。

## 二、总览页：集群整体情况

进入首页即「总览」。

1. **顶部筛选**：分区、节点状态（空闲 / 混合 / 占满 / 故障）、排序方式（GPU 使用率 / 负载 / 节点名）、
   视图（卡片 / 表格）。
2. **KPI 卡片**：GPU 使用数、利用率、运行/排队作业数、CPU/内存等。
3. **集群资源趋势**：右上角切换指标（GPU 平均利用率、GPU 使用数、运行作业数、排队作业数），
   右下角切换时间区间（5 分钟 / 15 分钟 / 1 小时 / 1 天）。
4. **用户排行榜**：按时间范围（1 天 / 7 天 / 30 天 / 全部）和指标排序：
   - `GPU 卡时 ↓`：谁占用的 GPU 时间最多
   - `作业数 ↓`
   - `GPU 利用率 ↓ 高→低` / `↑ 低→高`：后者用于发现**长期占卡但利用率低**的用户
   - 显示数量可选 Top 10 / Top 30

   **点击排行榜里的任意一行，会直接跳到该用户的「个人统计」页。**
5. **节点列表**：按卡片或表格展示每个节点的状态、GPU 占用、负载。
   **点击任意节点，会跳到该节点的「GPU 详情」页。**

## 三、GPU 详情页：单个节点看透

左上角选择节点（也可从总览页点击节点直接进来）。

1. **筛选栏**：节点、分区、粒度（1/5/15 分钟 / 1 小时）、
   **对比日期 A / B**（选两天可把曲线叠加对比，B 选「不对比」即单日）、
   GPU 卡（全部卡 / 指定某一张卡）。
2. **KPI 卡片**：该节点当前的 GPU 利用率、显存、温度、功耗、CPU、负载、内存。
3. **历史曲线对比**：切换指标（GPU 利用率 / 显存使用 / 节点负载 / 内存使用）。
   数据每 30 秒采集一次，按所选粒度聚合。
4. **GPU 卡实时状态**：每张卡一块，显示利用率、显存、温度、功耗、以及**卡上进程及其所属作业号**。
5. **作业列表**两个标签页：
   - **运行作业**：作业ID、用户、分区、GPU/CPU/内存、开始时间、运行时长、GPU 利用率
   - **等待排队**：GPU 需求、提交时间、已等待、等待原因、优先级、排队位次

   **点击表格中的用户名，直接跳到该用户的个人统计页。**

## 四、排队作业页：我为什么还没跑起来

用于回答「集群现在堵不堵、我的作业排在哪、卡在什么原因」。

1. **筛选**：用户、分区、目标节点、等待原因、GPU 需求（=1/=2/=4/≥8 卡）、排序（等待时长 / 优先级 / 提交时间）。
2. **KPI 卡片**：排队总数、最长等待、按 GPU 需求分布等。
3. **等待时长趋势**（15 分钟 / 1 小时 / 1 天粒度）与**等待原因分布**饼图。
4. **排队作业列表**：提交时间、等待时长、用户、作业ID、分区、GPU 需求、CPU/内存、
   目标节点、优先级、**排队位次**、**等待原因**。

常见等待原因：

| 原因 | 含义 |
|------|------|
| `Resources` | 等待资源释放（GPU/CPU/内存不够） |
| `Priority` | 优先级低，被前面高优先级作业挡住 |
| `NodeDown` | 目标节点故障/下线 |
| `Dependency` | 有依赖作业尚未完成 |

筛选条件里的「用户」下拉显示的是映射后的姓名；点击列表中的用户名可跳转到该用户的个人统计。

## 五、个人统计页：查看自己的使用率与作业分析

顶部导航 **「个人统计」**。这是最常用的页面，逐块说明。

### 1. 选择用户与范围

- **用户**：下拉框里是**映射后的姓名**（未映射的显示账号），或直接在「或输入」框输入账号后回车。
- **时间范围**：近 1 天 / 近 7 天 / 近 30 天（默认）/ 近 90 天 / 全部。
- **作业状态**：仅对「历史作业」生效，可筛 COMPLETED / FAILED / TIMEOUT / CANCELLED。
- **导出**：右上角可选 CSV 或 JSON，导出内容与当前页面筛选口径一致（用户、时间范围、作业状态、当前标签页）。

### 2. KPI 卡片（一眼看健康度）

| 指标 | 说明 |
|------|------|
| **GPU 总耗时** | 统计区间内累计 GPU 卡时 |
| **作业总数** | 含所有状态 |
| **成功率** | 完成数 / 总数，同时显示完成、失败个数；≥80% 显示为正常色 |
| **平均等待** | 从提交到开始调度，>15 分钟会标黄 |
| **当前运行 / 排队** | 实时作业数 |
| **GPU 平均利用率** | 按 GPU 时加权的实测利用率；**低于 40% 视为低效**会标黄。若区间内作业没有 GPU 实测数据，显示 `—` |

### 3. GPU 耗时趋势

右上角可切换 **粒度**（1 天 / 1 小时）和 **指标**：

- `GPU 耗时（卡时）` — 谁用了多少资源
- `作业数`
- `平均 GPU 利用率` — 看自己是否长期低效

> 归属口径：按**作业开始时间**归档，所以一个跨天作业的卡时会计入它开始的那一天。
> 选「全部」区间时，趋势图只展示最近 90 天。

### 4. 三个标签页

- **历史作业**（默认）：作业ID、作业名、分区、节点、GPU 卡数、开始/结束时间、耗时、等待、
  状态、**该作业的 GPU 利用率**。
  - 状态标签：`COMPLETED` 绿 / `FAILED` 红 / `TIMEOUT` 黄 / 其他灰。
  - 数组作业显示为 `141_54` 形式（父作业_子任务号）。
  - 底部分页，默认每页 20 条。
- **当前运行**：作业ID、作业名、分区、节点、GPU、CPU核/内存、开始时间、运行时长、实时 GPU 利用率。
- **排队中**：作业ID、作业名、分区、目标节点、GPU 需求、CPU/内存、提交时间、已等待、
  **等待原因**、**排队位次**。

### 5. 点开历史记录看作业分析（重点）

在「历史作业」或「当前运行」列表中，**点击行左侧的 `▸` 展开该作业的效率分析**（再点 `▾` 收起）。

展开后左右两部分：

**左：作业基本信息**

| 字段 | 说明 |
|------|------|
| 分区 / 节点数 / CPU 核 / GPU 数 | 资源申请 |
| 实际用时 / 申请时长 | 对比看是否申请过长 |
| **时间效率** | 实际用时 ÷ 申请时长。**<10% 很差（红），<25% 偏低（黄），≥25% 正常（绿）** |
| CPU 用量 / CPU 效率 / 内存峰值 | 当前显示 `n/a`（sacct 尚未采集该字段） |
| 申请内存 / AllocTRES | 申请的内存与原始分配记录 |

**右：GPU 运行分析**（来自 30 秒粒度的 GPU 采样，按作业号汇总）

- **GPU 利用率曲线**：作业运行期间每个采样点的利用率，标注采样点数
- **平均 GPU 利用率**：按颜色区分，数值越低越差
- **P90 利用率**：排除偶发尖峰后的"真实繁忙程度"
- **峰值显存（单卡）**
- **空转占比 (<10%)**：>30% 会标红，说明卡在空跑
- **GPU 效率评分**：0–100 的综合分，**<50 红、<75 黄、≥75 绿**
- **诊断**：如「存在明显空转」「利用率偏低」「正常」

下方还会给出**改进提示**（💡 条目），例如申请时长过长、利用率低、等待时间久等，
作业正常完成时显示「✓ 作业正常完成」。

> 如果 GPU 区域整块不出现，通常是因为该作业运行时间过短、或采集时没有拿到它的 GPU 快照，
> 此时会显示一条 `gpu_note` 说明原因。

### 6. 从别处快速跳转

以下位置点击用户名即可进入个人统计：

- 总览 → 用户排行榜的任意一行
- GPU 详情 → 节点作业列表（运行/排队）里的用户名
- 排队作业 → 排队列表里的用户名

## 六、用 rgtop 在命令行看实时 GPU（HTTP 模式）

[rgtop](https://github.com/xianull/rgtop) 是一个 btop 风格的终端面板，用它可以把多个节点的
GPU / CPU / 内存放进一个 TUI 里看。默认它靠 SSH 连到服务器采集；本系统实现了它的
**HTTP 后端**，所以你只要在能访问 Web 的机器上装一个二进制，**不需要 SSH 到算力节点**也能看实时数据。

### 1. 安装

macOS / Linux，x86_64 与 arm64：

```bash
curl -fsSL https://raw.githubusercontent.com/xianull/rgtop/main/install.sh | sh
```

装到 `~/.local/bin/rgtop`。若提示 `command not found`，把该目录加进 `PATH`：

```bash
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc   # zsh 用 ~/.zshrc
source ~/.bashrc
```

其他方式：从 Releases 下载 `rgtop-<arch>-<os>.tar.gz` 解压即可（单文件约 700 KB，无运行时依赖）；
升级用 `rgtop --update`，卸载就是删掉这个文件（配置在 `~/.config/rgtop/`）。

### 2. 确认服务端接口可用

```bash
# 列出所有可用节点（批量接口），rgtop 启动时就是请求这个
curl -s "http://192.168.3.102:8000/api/rgtop/frame?procs=0" | python3 -m json.tool | head -40

# 单节点，带每卡进程列表
curl -s "http://192.168.3.102:8000/api/rgtop/frame/h100-3?procs=1" | python3 -m json.tool
```

`procs=1` 返回每张卡上的进程（用户、命令行、显存），`procs=0` 省略进程（体积小约 56%）。
节点不存在返回 HTTP 404；节点已配置但还没采到数据时返回 200 且带 `error` 字段。

### 3. 告诉 rgtop 去哪里取数

只要条目**以 `http://` 开头**，rgtop 就走 HTTP 模式。三种写法，任选其一。

**写法一：只写服务地址（推荐，节点多时最省事）**

```bash
mkdir -p ~/.config/rgtop
cat > ~/.config/rgtop/hosts <<'EOF'
# 批量地址：rgtop 启动时拉一次节点列表，自动为每个节点生成条目
http://192.168.3.102:8000
EOF
```

**写法二：逐个节点写完整 URL**

```bash
http://192.168.3.102:8000/api/rgtop/frame/h100-3
http://192.168.3.102:8000/api/rgtop/frame/h200-1
```

节点名取自 `/frame/` 之后那一段。

**写法三：临时命令行参数 / 环境变量**

```bash
# 只跑这一次
rgtop http://192.168.3.102:8000/api/rgtop/frame/h100-3

# 用环境变量指定（空格或逗号分隔），适合写进 shell 启动文件
export RGTOP_HOSTS="http://192.168.3.102:8000"
```

命令行参数的优先级最高，其次是 `$RGTOP_HOSTS`，最后才是 `~/.config/rgtop/hosts`。
SSH 主机和 HTTP 地址可以混着写，rgtop 按前缀自动分派。

### 4. 常用命令

```bash
rgtop                     # 进入实时面板
rgtop -n 5                # 刷新间隔 5 秒（本系统 30 秒采一次，间隔调太小只是重复读同一帧）
rgtop -1                  # 打印一帧就退出，适合脚本/管道
rgtop --reset             # 忽略已保存的设置
```

进面板后：`←`/`→` 切换排序（按主机、空闲、剩余显存、最不忙），`f` 只看空闲卡，
`c`/`o`/`h`/`u`/`p` 开关 CPU 行、每核条带、利用率历史、USER 列、进程面板，
`l` 切成一行一台主机，`1`–`9` 折叠主机，`t` 切主题，`?` 看帮助，`q` 退出。
卡片页脚会标出数据年龄（如 `21.4s ago`）。

### 5. 注意事项

- **数据不是秒级的**：后端每 30 秒采集一次，接口结果还会缓存 10 秒，所以看到的是最近一帧。
  页面上显示的 `Ns old` 就是这个延迟，属正常现象。
- **必须用 `http://`，不支持 `https://`**：rgtop 当前不带 TLS 后端，写 https 会直接报错。
- **节点名不要用 `#`**：`~/.config/rgtop/hosts` 里 `#` 是注释起始符，
  `http://host:8000/#h100-3` 会被截断，节点名必须放在路径里。
- **批量地址拉不到节点会直接退出**（报 `cannot list nodes from ...`），
  而不是带着空列表启动 —— 遇到就先用上面的 `curl` 确认接口和网络。
- 节点名出现在列表里但显示无数据，通常是该节点刚加进「集群配置 → 节点映射」，
  还没完成第一次采集（最多等一个采集周期）。
- 通过 HTTP 只读数据、**没有任何写操作**，也不需要给使用者开节点的 SSH 权限。

## 七、常见问题

**Q：我在下拉框里找不到自己 / 名字还是账号？**
先在「名字映射」里给自己设置显示名；若已设置仍显示账号，刷新页面（下拉框在页面加载时填充）。

**Q：个人统计里没有我的历史作业？**
历史作业来自 sacct 同步，属于**准实时**（作业结束后由定时同步写入），刚结束的作业稍等一会再看。
同时确认顶部时间范围是否覆盖了作业时间。

**Q：GPU 利用率显示 `—`？**
该作业没有对应的 GPU 采样数据（运行时间过短、或采集时进程未能关联到作业号），不影响其他字段。

**Q：GPU 利用率只有 20%，是不是系统统计错了？**
利用率来自卡上实际进程的 NVML 读数，按 GPU 时加权。如果你申请了 8 卡但只用 1 卡，
加权后就会很低 —— 展开作业分析看「空转占比」和「诊断」，据此调整申请卡数。

**Q：作业ID 显示成 `141_54`？**
数组作业的子任务，`141` 是父作业号，`54` 是子任务号。

**Q：数据多久更新一次？**
实时指标 30 秒采集；趋势曲线按所选粒度聚合（1 分钟到 1 天）；
集群级趋势每 5 分钟聚合一次；页面接口带 15–60 秒缓存，短时间内可能看到相同数字。

**Q：页面上的数字和 `squeue` / `sacct` 对不上？**
排队与运行状态来自 slurmrestd 的实时快照，历史来自 sacct（集群本地时间已转为统一时区）。
若差异较大，请把节点名、作业号和时间点反馈给管理员。
